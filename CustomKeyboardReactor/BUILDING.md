# 빌드 및 검증

이 프로젝트의 기준 Unity 버전은 `6000.5.6f1`이며 Windows 64비트 플레이어를 대상으로 한다.

## 0단계 기준 설정

- 그래픽 API 자동 선택을 끄고 Direct3D 11만 사용한다.
- DWM 투명화를 위해 DXGI Flip Model Swapchain을 끄고 D3D11 BitBlt 모델을 사용한다.
- 플레이어는 창 모드로 시작하며 전체 화면 전환과 창 크기 조절을 끈다.
- 포커스를 잃어도 실행을 계속한다.
- 백그라운드 렌더링은 VSync 없이 초당 60프레임으로 제한한다.
- PC 렌더 파이프라인의 Depth Texture와 Opaque Texture를 사용하지 않는다.
- `Assets/Scenes/Overlay.unity`의 카메라는 알파 0으로 화면을 지운다.
- Edit Mode 테스트 결과는 `TestResults/EditMode.xml`에 기록한다.
- Windows 빌드는 `Builds/Windows/CustomKeyboardReactor.exe`에 생성한다.

## 1단계 투명 오버레이

- `OverlayWindowService`가 플레이어 창 핸들을 지연 획득한 뒤 DWM 투명화, 보더리스, 항상 위와 클릭 통과를 적용한다.
- 포커스와 디스플레이 구성이 바뀌면 창 속성을 다시 적용한다.
- 종료할 때 초기 창 스타일과 항상 위 상태를 복원한다.
- 1단계에서는 중앙의 청록색 불투명 이미지를 생성해 투명 배경과 렌더링 결과를 구분했다.
- 4단계부터 임시 검증 이미지는 기본 비활성화하고 저장된 활성 프리셋 이미지를 표시한다.
- 5단계부터 실제 캐릭터 이미지의 알파가 0.1 이상인 픽셀만 상호작용 영역으로 판정한다.

## Unity Editor 절차

1. `Custom Keyboard Reactor > Phase 0 > Configure Baseline`을 실행한다.
2. Unity Test Runner에서 Edit Mode 테스트를 실행한다.
3. `Custom Keyboard Reactor > Phase 0 > Build Windows 64-bit`을 실행한다.
4. `Builds/Windows/CustomKeyboardReactor.exe`를 실행해 현재 단계의 수동 검증을 진행한다.

## 1단계 완료 당시 수동 검증

이 절차는 임시 검증 이미지가 기본 활성화되어 있던 1단계 완료 시점의 기록이다. 현재 빌드는 활성 프리셋 이미지를 표시한다.

1. 바탕 화면에 클릭 결과를 확인할 수 있는 앱을 열어 둔다.
2. 빌드를 실행하고 창 테두리와 불투명 배경 없이 중앙의 청록색 이미지만 보이는지 확인한다.
3. 다른 창을 활성화해도 오버레이 이미지가 위에 유지되는지 확인한다.
4. 오버레이의 투명 영역을 클릭했을 때 아래 앱이 입력을 받는지 확인한다.
5. 청록색 이미지 위를 클릭했을 때 아래 앱이 입력을 받지 않는지 확인한다.
6. 작업 표시줄에서 오버레이를 다시 활성화한 뒤 투명화와 항상 위 상태가 유지되는지 확인한다.
7. 앱을 정상 종료하고 Unity 로그에 처리되지 않은 예외가 없는지 확인한다.

## 2단계 전역 입력 공급자

- `ActivityInputController`가 Windows 플레이어에서 키보드와 마우스 저수준 훅을 시작하고 종료 시 해제한다.
- 훅 콜백은 키 종류와 문자열을 전달하지 않고 반응 입력 발생 여부와 마우스 화면 좌표만 스레드 안전 큐에 기록한다.
- `ActivityInputCoordinator`는 메인 스레드에서 큐를 비우며 장치별 활성화, 설정 상태와 자체 UI 입력 제외 판정을 적용한다.
- 전체 입력 수는 `ActivityInputController.TotalInputCount`에서 확인한다.

## 2단계 수동 검증 준비

1. Unity Build Profiles에서 Windows 플랫폼의 `Development Build`와 `Script Debugging`을 켜고 플레이어를 빌드한다.
2. 빌드한 플레이어를 실행하고 IDE 디버거를 Unity Player 프로세스에 연결한다.
3. `ActivityInputController.TotalInputCount`를 조사식 또는 Watch에 등록한다.
4. 입력 지연을 비교할 수 있는 텍스트 편집기와 X1/X2 버튼을 확인할 수 있는 앱을 함께 준비한다.

## 2단계 수동 검증

1. 텍스트 편집기에 포커스를 둔 상태에서 문자키, 숫자키, 방향키, 수정키와 기능키를 한 번씩 눌러 입력마다 전체 입력 수가 1씩 증가하는지 확인한다.
2. 키 하나를 계속 눌러 자동 반복이 발생해도 키를 놓기 전에는 전체 입력 수가 추가로 증가하지 않는지 확인한다.
3. 키를 놓는 동작만으로 전체 입력 수가 증가하지 않는지 확인한다.
4. 왼쪽, 오른쪽, 가운데, X1과 X2 버튼을 눌러 각각 전체 입력 수가 1씩 증가하는지 확인한다.
5. 마우스 이동, 휠 회전과 버튼 해제만으로 전체 입력 수가 증가하지 않는지 확인한다.
6. `KeyboardReactionEnabled`와 `MouseButtonReactionEnabled`를 각각 끈 동안 해당 장치 입력이 집계되지 않고, 다시 켠 뒤 과거 입력이 뒤늦게 집계되지 않는지 확인한다.
7. `IsConfiguring`을 켠 동안 모든 입력이 집계되지 않고, 끈 뒤 과거 입력이 뒤늦게 집계되지 않는지 확인한다.
8. Windows `SendInput` 기반 자동화 도구로 생성한 키보드와 마우스 입력이 전체 입력 수에 포함되지 않는지 확인한다.
9. 입력을 빠르게 반복하면서 텍스트 편집기의 입력 반응과 포인터 동작에 체감 지연이 없는지 확인한다.
10. 플레이어를 정상 종료한 뒤 로그에 훅 시작 실패, 훅 해제 실패 또는 처리되지 않은 예외가 없는지 확인한다.

## 3단계 데이터와 프리셋 기반

- Windows 빌드는 실행 파일과 같은 폴더의 `UserData`를 사용자 데이터 루트로 사용한다.
- Unity Editor는 프로젝트 폴더를 오염시키지 않도록 `Application.persistentDataPath`를 계속 사용한다.
- 새 `UserData`가 없으면 이전 LocalLow 위치의 제품 데이터만 한 번 복사하고 기존 원본은 보존한다.
- `app-data.json`에는 스키마 버전, 활성 프리셋, 공용 설정과 전체 입력 수를 저장한다.
- JSON은 같은 폴더의 임시 파일을 완전히 기록한 뒤 기존 파일과 교체한다.
- 손상된 주 데이터는 `app-data.corrupt-{timestamp}.json`으로 보존하고 이전 정상 백업 또는 기본 데이터로 복구한다.
- 프리셋 이미지는 `presets/{preset-id}/images` 아래에 내부 ID 파일명으로 복사한다.
- 편집 중 가져온 이미지는 `drafts/{preset-id}/images`에 임시 보관하고 적용 시 프리셋 이미지 폴더로 확정한다.
- 프리셋 복제 이미지는 새 프리셋 폴더에 독립 복사하며, 프리셋 삭제 시 해당 소유 폴더를 제거한다.
- 첫 실행과 마지막 프리셋 삭제는 코드에 포함된 기본 프리셋 원본으로 새 편집 가능 프리셋을 만든다.
- Windows 플레이어는 시작 시 저장된 키보드·마우스 설정과 전체 입력 수를 불러오고 정상 종료 시 전체 입력 수를 저장한다.

## 3단계 자동 검증

1. 명령줄 절차의 Edit Mode 테스트를 실행한다.
2. `AppDataStoreTests`에서 첫 실행, 재로드, 이전 정상 데이터 복구와 미래 스키마 보호를 확인한다.
3. `PresetAssetStoreTests`에서 PNG/JPG/JPEG 가져오기, 초안 폐기, 읽기 가능한 텍스처와 독립 이미지 복제를 확인한다.
4. `PresetRepositoryTests`에서 활성 프리셋, 공용 설정, 이미지 소유권, 초안 적용과 전체 입력 수의 재실행 복원을 확인한다.
5. Windows 64비트 빌드를 실행해 플레이어 스크립트 컴파일과 패키징을 확인한다.

## 4단계 반응 상태 머신과 이미지 표시

- `ReactorStateMachine`이 반응, 대기와 설정 상태를 순수 C#으로 관리한다.
- 반응 상태 입력은 다음 일반 이미지로 순환하고, 대기 상태 입력은 첫 일반 이미지로 복귀한다.
- 대기 진입 시 직전 대기 이미지를 제외한 후보를 무작위로 선택한다.
- `CharacterPresenter`는 저장된 이미지를 읽기 가능한 텍스처로 캐시하고 화면 중앙의 아래쪽 중앙 기준점에 표시한다.
- 캐릭터 100%는 최대 320x320 UI 기준 픽셀이며, 최종 표시 영역은 현재 화면 짧은 변의 90%를 넘지 않는다.
- 5단계에서 선택한 모니터 작업 영역과 저장된 정규화 위치를 캐릭터 표시에 적용한다.

## 4단계 자동 검증

1. 명령줄 절차의 Edit Mode 테스트를 실행한다.
2. `ReactorStateMachineTests`에서 일반 이미지 순환, 대기 진입과 복귀, 직전 대기 이미지 제외, 설정 상태 정지와 환산 루프 수를 확인한다.
3. `CharacterScaleCalculatorTests`에서 5% 크기 단계, 10~300% 범위와 화면 90% 제한을 확인한다.
4. `CharacterPresenterTests`에서 Canvas와 캐릭터 이미지의 아래쪽 중앙 기준점을 확인한다.
5. Windows 64비트 빌드를 실행해 런타임 어셈블리와 UGUI 패키징을 확인한다.

## 4단계 수동 검증

1. 일반 이미지가 두 장 이상이고 대기 이미지가 한 장 이상인 저장 프리셋을 준비한다.
2. 플레이어 시작 직후 첫 일반 이미지가 화면 중앙에 표시되는지 확인한다.
3. 다른 앱에 포커스를 둔 채 키보드와 마우스 버튼을 눌러 입력마다 일반 이미지가 순환하는지 확인한다.
4. 대기 제한 시간 동안 입력하지 않아 대기 이미지로 전환되는지 확인한다.
5. 대기 상태에서 첫 입력 후 첫 일반 이미지로 복귀하는지 확인한다.
6. 캐릭터 크기를 바꾼 프리셋에서 이미지 비율과 아래쪽 중앙 기준점이 유지되는지 확인한다.
7. 플레이어를 정상 종료하고 로그에 처리되지 않은 예외가 없는지 확인한다.

2026-09-30 검증 결과: 일반 이미지 2장, 대기 이미지 1장과 캐릭터 크기 150%인 검증 프리셋으로 외부 포커스 입력 순환, 자동 반복 제외, 60초 대기 진입과 첫 입력 복귀를 확인했다. 정상 종료 후 전체 입력 수 64회 저장과 Player 로그 오류 없음도 확인했다.

4단계 당시에는 프리셋 편집 UI가 없어 `UserData/app-data.json`의 `RelativePath`와 실제 파일 경로를 직접 맞춰 검증했다. 현재는 6단계 설정 화면에서 이미지 추가와 순서 변경을 사용한다. 저장된 이미지 파일명과 상대 경로는 내부 ID이므로 직접 변경하지 않는다.

## 5단계 캐릭터 상호작용과 화면 배치

- `PointerHitTester`는 현재 이미지의 화면 좌표를 읽기 가능한 텍스처 픽셀로 변환하고 알파가 0.1 이상인 픽셀만 상호작용 영역으로 판정한다.
- `CharacterInteractionController`는 왼쪽 드래그, 우클릭 메뉴, 위치 잠금과 자체 마우스 입력 제외를 조정한다.
- 캐릭터 위치는 선택한 모니터 작업 영역 안에서 아래쪽 중앙 기준점의 정규화 좌표로 저장한다.
- 저장된 모니터가 사라지면 주 모니터를 선택하고 같은 정규화 위치를 작업 영역 안으로 보정한다.
- 활성 프리셋의 일반 이미지와 대기 이미지에서 알파가 0.1 이상인 픽셀 영역을 합쳐 프리셋 상호작용 경계로 사용한다.
- 프리셋 상호작용 경계는 화면 안에 유지하고 그 밖의 완전 투명한 여백은 화면 밖으로 이동할 수 있다.
- 우클릭 메뉴에서 위치 잠금, 다음 모니터 선택, 메뉴 닫기와 앱 종료를 실행할 수 있다.
- 우클릭 메뉴를 닫으면 설정 진입 전 상태와 표시 이미지를 유지하고 대기 타이머를 이어가며, 프리셋 적용 때만 첫 일반 이미지로 초기화한다.
- 2026-10-01 기준 전체 Edit Mode 테스트 78개와 `Builds/Windows/CustomKeyboardReactor.exe` Windows 64비트 빌드를 통과했다.

## 5단계 수동 검증

1. 투명 모서리가 있는 원형 PNG 프리셋으로 플레이어를 실행한다.
2. 이미지의 투명 모서리를 클릭해 아래 앱이 입력을 받고 전체 입력 수가 한 번 증가하는지 확인한다.
3. 이미지의 불투명 픽셀을 왼쪽 버튼으로 드래그해 캐릭터만 이동하고 해당 누름이 전체 입력 수에 포함되지 않는지 확인한다.
4. 앱을 재실행해 드래그한 위치와 선택한 모니터가 복원되는지 확인한다.
5. 불투명 픽셀을 오른쪽 클릭해 메뉴를 열고 위치 잠금을 켠 뒤 왼쪽 드래그가 시작되지 않는지 확인한다.
6. 메뉴에서 다음 모니터를 선택해 창과 캐릭터가 해당 모니터 작업 영역으로 이동하며 캐릭터 전체가 화면 안에 보이는지 확인한다.
7. 선택한 모니터를 분리하거나 사용할 수 없게 만든 뒤 앱을 실행해 주 모니터로 대체되고 캐릭터가 작업 영역 안에 보이는지 확인한다.
8. 모니터 배율 또는 디스플레이 구성을 바꾼 뒤 클릭 판정과 드래그 위치가 이미지 픽셀과 계속 일치하는지 확인한다.
9. 캐릭터를 화면 좌우와 위쪽 가장자리로 드래그해 완전 투명한 여백은 화면 밖으로 나가고 프리셋 상호작용 경계는 화면 안에 남는지 확인한다.
10. 일반 이미지를 순환하고 대기 이미지로 전환해도 캐릭터 기준점이 움직이지 않고 각 이미지의 상호작용 픽셀이 잘리지 않는지 확인한다.
11. JPG 프리셋에서는 이미지 사각형 전체가 상호작용 영역인지 확인한다.
12. 두 번째 이후 일반 이미지와 대기 이미지에서 각각 우클릭 메뉴를 열고 닫아 현재 이미지와 상태가 유지되는지 확인한다.
13. 메뉴의 닫기와 종료가 동작하고 정상 종료 후 Player 로그에 처리되지 않은 예외가 없는지 확인한다.
14. 서로 해상도 또는 작업 영역 크기가 다른 두 모니터에서 `1번 -> 2번 -> 1번 -> 2번` 순서로 반복 전환한다.
15. 매 전환 후 메뉴가 캐릭터와 같은 상대 위치에 있고 캐릭터와 메뉴의 불투명도가 변하지 않는지 확인한다.

2026-10-01 검증 결과: Intel 출력 125% DPI 주 모니터와 NVIDIA 출력 100% DPI 보조 모니터에서 저장된 보조 모니터 시작과 `1번 -> 2번 -> 1번 -> 2번` 반복 전환을 확인했다. 캐릭터와 메뉴의 원본 RGB 값, 상대 위치와 불투명도가 모든 전환에서 유지됐고 Player 로그에 처리되지 않은 예외가 없었다.

2026-10-01 투명 여백 배치 검증 결과: `Tempdata`의 일반 이미지 6장과 대기 이미지 1장은 모두 500x500px이며, 알파 0.1 이상 픽셀의 합집합은 가로 73~407px, 세로 전체 기준 하단 0px부터 상단 약 469px 범위다. 합성 픽셀을 사용하는 Edit Mode 테스트 77개와 Windows 64비트 빌드를 통과했고 실제 화면 가장자리 드래그 및 일반·대기 전환도 사용자 확인을 완료했다.

2026-10-01 설정 닫기 상태 복원 검증 결과: 상태 머신 테스트 16개와 전체 Edit Mode 테스트 78개, Windows 64비트 빌드를 통과했다. 기본 빌드에는 사용자 프리셋 데이터가 포함되지 않으므로 일반 및 대기 이미지를 사용한 우클릭 메뉴 Standalone 통합 검증은 6단계 프리셋 편집 UI 완료 후 진행한다.

## 6단계 설정과 프리셋 편집 UI

- 캐릭터를 우클릭한 뒤 `설정 열기`로 설정 화면에 진입한다.
- 프리셋 목록에서 선택한 항목은 초안으로 미리 보고, `적용`할 때 저장 및 활성화한다.
- 새 프리셋은 일반 이미지를 한 장 이상 가져와야 적용할 수 있다.
- 일반 이미지 썸네일은 드래그 또는 좌우 명령으로 정렬하며 대기 이미지도 추가 및 삭제할 수 있다.
- 캐릭터 크기, UI 크기와 공용 설정은 각각의 저장 경계를 사용한다.
- 변경 후 프리셋 전환, 닫기 및 종료는 적용·버리기·취소를 확인한다.
- 공용 설정에서 카운트 및 전체 데이터 초기화는 별도 확인을 거친다.
- TMP 필수 리소스를 포함하며 OS의 맑은 고딕을 동적 TextMeshPro 글꼴로 사용한다. 기본 리소스를 다시 준비할 때는 `Custom Keyboard Reactor > Settings > Prepare UI Resources`를 실행한다.

자동 검증은 격리된 파일시스템의 초안 적용, 폐기, 저장 실패 재시도, 원본 없는 재실행 복원 및 전체 초기화를 포함한다. 설정 UI 명령과 넓은·좁은 화면 및 공용 설정 렌더링도 Edit Mode에서 검증한다. 결과는 `TestResults/EditMode.xml`, 화면 캡처는 `TestResults/SettingsUi-*.png`에 기록한다.

2026-10-01 검증 결과: 최종 Edit Mode 테스트 102개가 모두 통과했고 Windows 64비트 빌드도 종료 코드 0으로 성공했다. UI 선택·적용·버리기·취소와 연속 공용 설정 변경을 실제 UI 명령으로 확인했다. Windows 빌드 종료 시 Unity Version Control의 GUI 종료 경고가 기록됐으나 빌드 실패 또는 제품 스크립트 컴파일 오류는 없었다. 아래 Standalone 수동 검증은 아직 수행하지 않았다.

### Windows 수동 검증

1. 우클릭 메뉴에서 설정을 열고 PNG/JPG/JPEG 파일로 새 프리셋을 만든다.
2. 일반 이미지 두 장 이상과 대기 이미지 한 장 이상을 추가하고 일반 썸네일을 드래그해 정렬한다.
3. 이름, 크기와 호버 문구를 편집하고 적용한다. 설정 화면이 열린 동안 입력이 집계되지 않는지 확인한다.
4. 닫은 뒤 외부 앱 입력으로 일반 이미지가 정렬 순서대로 순환하는지 확인한다.
5. 두 번째 이후 일반 이미지와 대기 이미지에서 각각 설정을 열고 정상 닫기 또는 버리기를 선택해 이전 상태 및 이미지가 유지되는지 확인한다.
6. 변경 후 프리셋 전환, 닫기와 종료에서 취소가 현재 초안과 화면을 유지하는지 확인한다.
7. 원본 이미지 파일을 별도 위치로 옮긴 뒤 재실행해 적용한 프리셋과 이미지가 복원되는지 확인한다.
8. UI 크기 50%, 100%, 200%에서 스크롤, 입력 필드, 드롭다운과 메뉴를 조작하고 캐릭터 크기가 독립적으로 유지되는지 확인한다.
9. 다른 DPI의 모니터로 이동하고 설정 화면 및 메뉴의 포인터 판정이 맞는지 확인한다.
10. 카운트 초기화가 프리셋을 유지하고, 전체 초기화와 마지막 프리셋 삭제가 편집 가능한 기본 프리셋을 생성하는지 확인한다.

이 Windows 수동 검증을 마치기 전에는 개발 순서 6단계를 완료로 표시하지 않는다.

## 명령줄 절차

저장소 루트의 PowerShell에서 다음 명령을 실행한다. Unity 설치 경로가 다르면 `$unityEditor` 값만 바꾼다.

```powershell
$unityEditor = "C:\Program Files\Unity\Hub\Editor\6000.5.6f1\Editor\Unity.exe" # Unity Editor 실행 파일 경로
$projectPath = Join-Path $PWD "CustomKeyboardReactor" # Unity 프로젝트 루트 경로

$buildArguments = @( # Windows 빌드 인자
  "-batchmode",
  "-quit",
  "-projectPath", "`"$projectPath`"",
  "-executeMethod", "CustomKeyboardReactor.Editor.Build.PhaseZeroBuild.BuildWindows64",
  "-logFile", "`"$projectPath\Logs\PhaseZeroBuild.log`""
)
$buildProcess = Start-Process -FilePath $unityEditor -ArgumentList $buildArguments -WindowStyle Hidden -Wait -PassThru # 동기 빌드 프로세스
if ($buildProcess.ExitCode -ne 0) { throw "Windows build failed with exit code $($buildProcess.ExitCode)." }

New-Item -ItemType Directory -Path "$projectPath\TestResults" -Force | Out-Null
$testArguments = @( # Edit Mode 테스트 인자
  "-batchmode",
  "-projectPath", "`"$projectPath`"",
  "-executeMethod", "BreadPack.Mcp.Unity.McpServerBootstrap.StopServer",
  "-runTests",
  "-testPlatform", "EditMode",
  "-testResults", "`"$projectPath\TestResults\EditMode.xml`"",
  "-logFile", "`"$projectPath\Logs\EditModeTests.log`""
)
$testProcess = Start-Process -FilePath $unityEditor -ArgumentList $testArguments -WindowStyle Hidden -Wait -PassThru # 동기 테스트 프로세스
if ($testProcess.ExitCode -ne 0) { throw "Edit Mode tests failed with exit code $($testProcess.ExitCode)." }
```

배치 테스트에서는 Unity MCP의 TCP 서버를 먼저 정지해 테스트 종료와 서버 연결 정리가 경합하지 않게 한다. 두 명령의 종료 코드가 `0`이어야 하며, Unity Console과 로그에 컴파일 오류 또는 처리되지 않은 예외가 없어야 한다.
